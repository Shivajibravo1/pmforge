## Friday, the stand-up where you nodded

It is the Friday stand-up. Rahul Mehta, your lead developer, is giving his update. You are writing notes and nodding.

```chat
# Stand-up, Friday, 9:15 AM
Rahul Mehta | Lead developer | The fix is in dev, it passed in test, but staging is still on the old build and the vendor's API is rate-limiting us.
Priya Nair | Service desk lead | So can staff log in or not?
Rahul Mehta | Lead developer | In dev yes. In staging no. Production is untouched.
Daniel Okafor | Sponsor | Great. So we are on track?
```

Everyone looks at you. You said "good" a few seconds ago, and you are not sure what you approved. If you understood about half, you are normal. Daniel just asked you to confirm status based on a sentence you could not translate.

```note
You do not need to be an engineer. You need enough fluency to ask good questions and to notice when an answer does not add up.
```

## Four ideas to own

```cards
workflow | SDLC | The software development life cycle: plan, design, build, test, release, operate. Know where your project is and what must be true to move on. | Skipping a stage hides defects until production.
layers | Environments | Separate copies of the system: development, test, staging, production. Each has a purpose. | Testing in one place and assuming it works in another.
link | APIs | A defined way for one system to ask another for data or actions. Most integrations are APIs. | A vendor change breaks you with no warning.
cloud | Cloud | You rent computing and services instead of owning servers. The provider secures the platform, you secure your use of it. | Assuming the provider secures your data and settings.
```

```ref
NIST | SP 800-145 definition of cloud computing: essential characteristics, IaaS, PaaS, SaaS | Gives you the exact vocabulary to explain who runs what in IaaS, PaaS and SaaS. Useful when a vendor blurs the line.
```


## Environments: translate Rahul's sentence

Think of a restaurant. The chef tries a new dish in the test kitchen, then serves it to staff, then puts it on the menu. Software does the same.

```flow
Developer laptop | Code is written and tried by one person
Test | Automated and manual checks run
Staging | Production-like rehearsal
Production | Real users, real data
```

Now read Rahul's sentence again. Fixed in dev, passed in test, not in staging, nothing live. The honest status is amber. The login fault is not fixed where it matters.

```rag
Fix built | G | Works in development and test
Staging release | A | Old build still deployed, needs a release slot
Vendor API | A | Rate limits slow testing, vendor contacted
Production | G | Untouched, no customer impact today
```

A problem found in test costs little. The same problem found in production costs a lot more and hits real customers. So always ask which environment a result came from.

```ref
ITIL | ITIL 4 release management and deployment management practices | Use them to explain how a change moves through dev, test and production, and who signs each step.
DORA | DORA delivery metrics: deployment frequency, lead time, change failure rate, time to restore | Ask for these four numbers to judge a delivery team without reading code.
```


## Your decision

Daniel asked "so we are on track?" The room is waiting.

```decision
? What do you say to Daniel in front of the team?
- "Yes, on track." Rahul said it passed in test | You repeat a green status that is actually amber. In week 3 staging fails and Daniel remembers you said on track.
- "I need an engineer to explain before I answer" and end the meeting | You look unsure in front of the sponsor and the team loses a day of momentum.
+ "Fixed in test, not yet in staging, so amber. Rahul, what do you need to get it to staging, and by when?" | Daniel gets an honest colour, Rahul gets a clear ask with a date, and the room sees a PM who understands the path to production.
= Translate, then commit to a next step. You do not need to know how the fix works. You need to know where it is, what blocks it and who is moving it.
```

## APIs and the cloud

When Rahul says "the vendor's API is rate-limiting us", ask three things: who owns it, what availability do they promise, and what happens to us if it changes.

```key
Shared responsibility: the cloud provider secures the underlying platform. You remain responsible for your data, who can access it, and how it is configured.
```

```arch
# Shared responsibility in the cloud (typical model, exact split depends on the service)
You manage | Your data, Identity and access, Configuration, Your applications
Provider manages | Servers and virtualisation, Storage and networking, Data centres and power
```

```ref
OWASP | API Security Top 10 | When a project exposes or consumes APIs, ask the team which of these risks they tested. A credible security question from a non-engineer.
Azure | Well-Architected Framework pillars: reliability, security, cost optimization, operational excellence, performance efficiency | Use the pillars as a review checklist for any cloud design. The AWS Well-Architected Framework is the equivalent.
```


## An AI model is an API too

The Nimbus assistant is not built from scratch. It is a vendor model called over an API. Every question above applies, plus a few new ones.

```cards
link | The model is a vendor service | Ask who owns it, how available it is, and what happens when the vendor changes it. | The model changes and your outputs shift overnight.
lock | Data leaves your boundary | Prompts can contain customer or internal data. | Confidential data goes to a service with no contract or approval.
eye | Evidence and logs | Keep a record of how the AI was used and what it returned. | Nobody can explain why it said that when asked.
```

```ai
Shift | AI models are consumed like any cloud service through an API, with keys, limits, versions, cost and a shared responsibility model.
Example (illustrative) | A developer says the assistant works in test. The PM asks which environment, which keys and which data, and finds it points at production data.
Use AI to | Explain a technical term in plain words, summarise an architecture document and prepare questions for a developer.
Keep human | Judging whether an explanation fits your system. A confident answer can still be wrong for your environment.
Risk | Keys in code or chat, tests pointed at production, and data sent to a model service nobody assessed.
Control | Separate environments, least privilege access, secrets in a managed store and a review of what leaves your organisation.
Interview line | Shared responsibility applies to AI services too. The vendor runs the model, and I own what goes in, who can use it and how we check what comes out.
```

```ref
OWASP | Top 10 for Large Language Model Applications | Name it when someone says an AI model is just another API. It lists risks such as prompt injection that an ordinary API does not have.
```

```cards
network | Integration engineer | Connects systems through APIs and handles errors, limits and versions. | Surprised by a model API rate limit in production.
key | Security engineer | Manages keys, tokens and access to APIs and environments. | Keys kept in code or shared in chat.
cpu | AI engineer | Chooses models, prompts and retrieval and tests them in a non production environment. | Testing against production data.
handshake | Forward deployed engineer | Deploys into the customer's environments, often with limited access. | Manual changes that bypass the release process.
wrench | Agent harness engineer | Defines which tools and APIs an agent may call. The term is not standardised, so confirm the scope. | An agent allowed to call more than it needs.
```

```incident
# Test agent connected to a production system (illustrative)
What happened | An engineer testing an AI agent pointed it at the production ticket system because the test environment was not ready.
Impact | The agent created and changed real tickets, and support staff spent a day cleaning up.
Root cause | Environments were not separated clearly, and the agent had write access it did not need for testing.
Resolution | The test environment was completed, the agent was moved to read only access, and production credentials were restricted to the release process.
PM move | Ask which environment every test uses and what access it has. Treat AI agents like any integration.
```

## Questions that make you credible

Keep these in your pocket. Each one takes ten seconds and each has saved a real project.

```accordion
Which environment is this demo running in? | Tells you how much the result proves. A demo in development says little about production.
What is the rollback plan if the release fails? | A release without a tested way back is a gamble with other teams' systems.
Which other systems call this API? | Reveals hidden dependencies that a change can break.
Who has production access and how is it approved? | A basic security and audit question that a CISO will ask anyway.
What is not tested yet? | Forces an honest list of gaps instead of a green dashboard.
```

```ref
CIS | Controls v8, inventory and control of enterprise and software assets | Asking whether we know every system and app in scope is a CIS first step and shows security awareness.
```
