## 11:42 PM: the release has failed

The Nimbus assistant release started at 10:30 PM. By 11:42 PM, the checkout service is returning errors for about one in five customers. The release manager is on the line. So are the sponsor, the lead developer and the operations lead. You have to decide.

This is a simulation. Each choice has consequences, and the best answer is a judgement about evidence, time and people.

```chat
# Release bridge, Friday, 11:42 PM
Rahul Mehta | Lead developer | Error rate is at twenty percent on checkout. It started with the release.
Operations lead | Operations | Rollback takes about twenty minutes. The database migration ran, and I am not sure the old version works with it.
Daniel Okafor | Sponsor | The campaign emails go out at six. We cannot have broken checkout.
Elena Rossi | CISO | If we roll back, do we lose the security fix in this release?
```

## The facts you have

```rag
Customer impact | R | One in five checkouts failing
Cause | A | Likely the new release, not confirmed
Rollback | A | Twenty minutes, database compatibility uncertain
Fix forward | A | Rahul has a suspected fix, untested
Deadline | A | Campaign emails at six in the morning
```

```key
In a live failure, protect customers first, then find the cause. Prefer the option you can reverse and measure over the one that looks clever.
```

```ref
DORA | Time to restore service | Use the metric to explain why restoring service first can beat fixing forward.
```


## The options

```flow
Rollback now | Return to the last known good version
Fix forward | Deploy a quick patch to the new version
Disable the feature | Turn off the new feature with the flag, keep the release
Stop and wait | Gather more data before acting
```

```ref
ITIL | ITIL 4 change enablement, emergency change, and incident management | A rollback is a change with an emergency route. Record who approved it.
NIST | SP 800-34 contingency planning | Predefined rollback criteria make a night time decision easier.
```

```arch
# A production deployment and its safety nets

~Plan | Rollback tested before release, Decision owner named
```

## Your decision

```decision
? What do you decide at 11:45 PM?
- Fix forward with Rahul's untested patch | You add a second untested change to a failing system, at midnight.
- Do nothing until morning and investigate | Customers keep failing for hours, and the campaign hits a broken system.
- Roll back immediately without checking the database | If the old code cannot read the migrated data, you make the outage worse.
+ Turn off the new feature with the flag now to reduce impact, ask operations to confirm database compatibility for rollback in parallel, and set a decision point in fifteen minutes for rollback if errors persist | You cut customer impact in minutes with a reversible step, while you check the safe way back.
= Use the fastest reversible action to stop the harm, then verify the safe full rollback. Set a time limit on the decision.
```

## Lessons

```cards
flag | Feature flags are fast | They gave you a safe first step. | Lacking one makes every release an all or nothing bet.
database | Rollback and data | Check data compatibility before you need it. | Rollback plans that ignore migrations.
clock | Time boxing | Fix a point to review the decision. | A long debate while customers suffer.
book | Blameless review | Fix the process, not the person. | Fear that hides future problems.
```

```incident
# Rollback restored code but not the prompt version (illustrative)
What happened | A release failed at night and the team rolled back the application. The AI prompt configuration stayed at the new version.
Impact | The old code ran with the new prompts and produced wrong output until the mismatch was found.
Root cause | Prompt and model versions were not part of the release package and rollback.
Resolution | The team included prompt and model versions in the release artefact and added a post rollback check.
PM move | Roll back code, prompts and model settings together and verify after.
```

```answer
? A production release has failed late at night. Do you roll back or fix forward?
- Always fix forward | It can extend the outage.
- Always roll back | It may not be possible or may lose data.
+ I confirm facts and impact, then decide with the incident owner using criteria: is rollback tested and safe, is the cause understood, what is the customer impact and how long would a fix take. I default to rollback when it is safe and tested, communicate on a set cadence, record the decision and hold a review. For AI I roll back prompt and model versions too.
= Facts first.
= Criteria for the choice.
= Communicate and record.
```
