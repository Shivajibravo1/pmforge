## Three ways to organise delivery

```cards
map | Predictive (waterfall) | Plan the full scope first, then build in phases. Suits stable requirements, fixed contracts and regulated change.
rocket | Agile | Short cycles, real feedback, frequent reprioritising. Suits uncertain requirements and evolving products.
layers | Hybrid | Fixed governance and budget gates around iterative delivery. Most enterprises run hybrid whether they admit it or not.
```

```flow
Requirements | Fixed up front
Design | Agreed before build
Build | Phased delivery
Test | Late, large
Deploy | One big release
```

## How to choose

| Question | Leans predictive | Leans agile |
| --- | --- | --- |
| Are requirements stable and well understood? | Yes | No |
| Is the cost of late change high (hardware, regulation)? | Yes | No |
| Can users give frequent feedback? | No | Yes |
| Does the contract fix scope and price? | Yes | Flexible |
| Is the team experienced with iterative delivery? | No | Yes |

## What stays the same

Whatever lifecycle you pick, you still need a clear goal, an accountable sponsor, a risk process, quality checks and a controlled path to production. The lifecycle changes how often you plan and inspect, not whether you do.

```warn
Calling a project agile while approving a fixed scope, fixed date and fixed budget with no flexibility anywhere. Something has to flex. If nothing can, you are running a predictive project and should plan and report it that way.
```

```quiz
? Scope, date and budget are all fixed by contract. Which label is honest?
+ Predictive, planned and reported as such
- Agile, because we hold daily stand-ups
- Hybrid, because we use Jira
= Ceremonies do not make a project agile. If nothing can flex, plan it predictively.
```
