## Same goal, three ways to get there

Your sponsor says: "We need a new booking system in six months."

There are three sensible ways to run it, and picking the wrong one is how projects end up late for reasons nobody can explain.

## The three approaches

```cards
map | Predictive (waterfall) | Plan everything first, then build in order: requirements, design, build, test, deploy. Like building a house from fixed drawings. | Problems surface late, when change is expensive.
rocket | Agile | Build in short cycles, show real software often, change direction based on feedback. Like a restaurant testing a menu with customers. | With no clear goal, the work never feels finished.
layers | Hybrid | Fixed budget and approval gates around iterative delivery. Most enterprises run this, even if they do not call it that. | Nobody knows which rules apply where.
```

```flow
Requirements | Agreed up front
Design | Signed off
Build | In phases
Test | Late and large
Deploy | One big release
```

## How to choose

You do not pick by fashion. You pick by answering five questions about your project.

| Question | Leans predictive | Leans agile |
| --- | --- | --- |
| Are requirements stable and well understood? | Yes | No |
| Is the cost of late change high (hardware, regulation)? | Yes | No |
| Can users give frequent feedback? | No | Yes |
| Does the contract fix scope and price? | Yes | Flexible |
| Is the team experienced with iterative delivery? | No | Yes |

## AI changes the build, not the rules

Your developers now use AI coding assistants. The build phase gets faster. Does your lifecycle choice change? Not the choice, but where the pressure lands.

```cards
code | Faster first drafts of code | Developers produce a working version sooner. | More code arrives to be reviewed, so review and testing become the bottleneck.
check | AI-suggested tests | An assistant proposes test cases from the code. | It tests what the code does, not what the business needs.
clock | AI-assisted estimates | A quick sanity check on effort. | It does not know your team's real pace or your hidden dependencies.
```

```ai
Interview line: "AI shortens the build, so I move my control point to review, testing and release." Your approval gates stay. Their evidence changes.
```

## What never changes

Whatever you pick, you still need a clear goal, an accountable sponsor, a way to manage risk, quality checks and a controlled path to production. The approach changes how often you plan and check. It never removes the need.

## The classic trap

```warn
Calling a project agile while the contract fixes scope, date and budget with no flexibility anywhere. In every project something has to flex. If nothing can, you are running a predictive project. Plan it and report it that way.
```

## Check your understanding

```quiz
? Scope, date and budget are all fixed by contract. Which label is honest?
```

## What to remember

```checklist
Predictive: plan first. Agile: learn in short cycles. Hybrid: gates around iteration
Choose using the five questions, not by fashion
Every approach still needs goal, sponsor, risk process, quality checks, release control
If nothing can flex, it is not agile
```
