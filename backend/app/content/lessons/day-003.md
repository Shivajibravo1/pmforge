## Thursday, the contract on your desk

Nimbus has a type and workstreams. Now Daniel drops a new problem on your desk. The AI vendor sent a contract. It fixes the scope, the price and the go-live date. In the same email, Daniel writes: "We are an agile company, so let us run this one agile."

You read the contract twice. Then you call Rahul Mehta, your lead developer.

```chat
# Call with the lead developer, Thursday, 2:30 PM
Rahul Mehta | Lead developer | Agile is great. But if the vendor delivers a fixed list on a fixed date, who decides what to drop when we are late?
Daniel Okafor | Sponsor | Nobody drops anything. We want everything by the date.
Rahul Mehta | Lead developer | Then it is not agile, it is waterfall with stand-ups. I have seen it end badly.
```

This is the trap behind the word "agile". The approach you pick decides how you plan, how you report and how change gets handled. Picking by fashion is how projects end up late for reasons nobody can explain.

## Three ways to run the same project

```cards
map | Predictive (waterfall) | Plan everything first, then build in order: requirements, design, build, test, deploy. Like building a house from fixed drawings. | Problems surface late, when change is expensive.
rocket | Agile | Build in short cycles, show real software often, change direction based on feedback. Like a restaurant testing a menu with customers. | With no clear goal, the work never feels finished.
layers | Hybrid | Fixed budget and approval gates around iterative delivery. Most enterprises run this, even if they do not call it that. | Nobody knows which rules apply where.
```

```flow
Requirements | Agreed up front
Design | Signed off
Build | In phases
Test | Late and large
Deploy | One big release
```

That flow is predictive. Agile repeats a small version of it every two weeks or so, so feedback arrives while change is still cheap.

```ref
PMI | Agile Practice Guide, the lifecycle spectrum: predictive, iterative, incremental, agile | Use the spectrum words precisely. Interviewers notice when a candidate says hybrid without being able to say what is predictive and what is agile.
Scrum | Scrum Guide, the Sprint, its events and its artifacts | Know the five events and three artifacts in one breath. It is a frequent agile question in PM interviews.
```


## How to choose

You do not choose by fashion. You answer five questions about your project.

| Question | Leans predictive | Leans agile |
| --- | --- | --- |
| Are requirements stable and well understood? | Yes | No |
| Is the cost of late change high (hardware, regulation)? | Yes | No |
| Can users give frequent feedback? | No | Yes |
| Does the contract fix scope and price? | Yes | Flexible |
| Is the team experienced with iterative delivery? | No | Yes |

Now score Nimbus. Scope is fixed by contract. The assistant's behaviour is not well understood yet. Customers can give feedback only after a pilot. Elena requires fixed security gates. That is a mix, which is why hybrid fits.

## Your decision

```decision
? Daniel wants "agile", the contract fixes scope, price and date, and Elena needs formal security gates. What do you propose?
- Call it agile and run two week sprints, keeping everything else fixed | You report agile, but nothing can flex. In week 10 the team is behind, there is no scope to cut, and Daniel asks why "agile" did not help.
- Run pure waterfall with a signed requirements document and no demos until testing | Elena is happy, but the assistant's behaviour is only discovered in testing, when changes cost the most.
+ Run hybrid: fixed contract, budget and security gates, with two week sprints for the portal and assistant and a demo to real staff at the end of each | Daniel sees working software every fortnight, Elena keeps her gates, and the contract fixes the envelope while the team decides the order inside it.
= Hybrid is honest when parts of the project are fixed and parts are uncertain. Say out loud what is fixed and what flexes, and report against both.
```

## What the first month looks like

```timeline
Week 1 | Contract signed. Scope, price and date fixed. Gate dates agreed with security | ok
Week 2 | First sprint demo. Staff can log in to a test portal | ok
Week 4 | The assistant gives a wrong delivery date in a demo. Team adds a human fallback story | warn
Week 6 | Security gate 1 passed on time because evidence was built into every sprint | ok
Week 9 | Pilot with 50 staff. Feedback changes two screens, nothing breaks the contract | ok
```

Notice what the hybrid choice bought: early feedback on the assistant, and gates that are met because evidence is produced every sprint.

## AI changes the build, not the rules

Rahul's team now uses AI coding assistants. The build gets faster. Your lifecycle choice stays. The pressure moves.

```cards
code | Faster first drafts of code | Developers produce a working version sooner. | More code arrives to be reviewed, so review and testing become the bottleneck.
check | AI-suggested tests | An assistant proposes test cases from the code. | It tests what the code does, not what the business needs.
clock | AI-assisted estimates | A quick sanity check on effort. | It does not know your team's real pace or your hidden dependencies.
```

```ai
Shift | AI shortens parts of the build, so delivery speed rises but so does the pace of mistakes. Control moves to review, testing and release.
Example (illustrative) | A team uses AI to write code faster. Review and testing become the bottleneck, so the PM adds reviewers and an automated test stage before the next release.
Use AI to | Draft user stories, generate test ideas, summarise sprint results and compare how predictive, agile and hybrid plans would run.
Keep human | The choice of lifecycle, the approval gates and the call on whether an iteration is good enough to release.
Risk | Treating AI output as finished work and skipping reviews because the first draft looks professional.
Control | Keep approval gates. Change the evidence they ask for: evaluation results, test coverage and an owner who signs the release.
Interview line | AI shortens the build, so I move my control point to review, testing and release. My gates stay and their evidence changes.
```

```ref
NIST | SP 800-218 Secure Software Development Framework (SSDF) | AI-assisted code still needs secure development practice. Cite SSDF when a client asks who checks AI generated code.
```

```cards
cpu | AI engineer | Works in short experiments with evaluations. Fits agile, but needs a quality threshold. | Experiments with no definition of enough.
handshake | Forward deployed engineer | Brings real customer feedback into each iteration. | Feedback collected but not prioritised.
wrench | Agent harness engineer | Builds guardrails and evaluations around an agent. The term is not standardised, so confirm the scope. | Controls added late, after the contract scope was fixed.
shield | AI security consultant | Reviews each iteration for new data and tool risks. | One review at the end of a predictive plan.
code | Traditional developers | Often work to fixed interfaces that agile AI teams keep changing. | Interface changes with no change control.
```

```incident
# Fixed scope contract, uncertain AI behaviour (illustrative)
What happened | A fixed scope, fixed price contract was signed for an AI assistant. During build, the team found that the first approach to retrieval gave poor answers.
Impact | Change requests multiplied and the vendor relationship soured.
Root cause | A predictive contract was used for work whose feasibility was unknown.
Resolution | The parties moved to a hybrid model: a fixed discovery phase, then iterative delivery with a capped budget and an accuracy threshold.
PM move | Match the lifecycle and contract to certainty. Use hybrid when part of the work is uncertain.
```

## What never changes

Whatever you pick, you still need a clear goal, an accountable sponsor, a way to manage risk, quality checks and a controlled path to production. The approach changes how often you plan and check. It never removes the need.

```warn
Calling a project agile while the contract fixes scope, date and budget with no flexibility anywhere. In every project something has to flex. If nothing can, you are running a predictive project. Plan it and report it that way.
```

## Check your understanding

```quiz
? Scope, date and budget are all fixed by contract. Which label is honest?
+ Predictive, planned and reported as such
- Agile, because we hold daily stand-ups
- Hybrid, because we use Jira
= Ceremonies do not make a project agile. If nothing can flex, plan it predictively.
```

```answer
? How do you choose between predictive, agile and hybrid delivery?
- Agile for everything, it is modern | Ignores fixed regulatory dates, contracts and hardware dependencies.
- Predictive for everything, it is safer | Slow to react when scope is uncertain, as with AI features.
+ I choose by certainty and constraints. Stable scope, fixed contracts and long lead times favour predictive. Uncertain scope and fast feedback favour agile. Most enterprise work is hybrid: plan the fixed parts and iterate the uncertain parts. For AI features I use short iterations with an evaluation threshold, inside a plan that still tracks cost and dates.
= Say what drives the choice: certainty, contracts and regulation.
= Mention hybrid early, because most enterprises use it.
= Be ready to name one thing that never changes: outcome, risk and stakeholders.
```

## What to remember

```checklist
Predictive: plan first. Agile: learn in short cycles. Hybrid: gates around iteration
Choose using the five questions, not by fashion
Say out loud what is fixed and what flexes
Every approach still needs goal, sponsor, risk process, quality checks, release control
If nothing can flex, it is not agile
```


```mindmap
# Delivery lifecycles
Predictive | Fixed scope, stage gates, strong documentation
Agile | Iterations, feedback, changing scope
Hybrid | Fixed plan for stable parts, iterations for uncertain parts
Never changes | Outcome, risk, stakeholders, accountability
```
