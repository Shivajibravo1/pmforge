## "It works" is not an acceptance criterion

User testing for Nimbus begins next week. Marcus asks the question that makes everyone uncomfortable.

```chat
# Test planning, Thursday, 3:15 PM
Marcus Webb | Business analyst | What does passed mean? If a tester says it looks fine, do we sign off?
Priya Nair | Service desk lead | My team will be using this daily. Fine is not good enough for us.
Rahul Mehta | Lead developer | We have unit tests. Those pass.
Elena Rossi | CISO | Unit tests passing does not answer my question either.
```

Quality is not a phase you add at the end. It is a set of agreed conditions, decided before building, that tell everyone when work is good enough. If you leave it to the end, the people building and the people accepting have different pictures, and the argument happens at the worst moment.

```key
Quality is fitness for purpose, defined in advance and checked by evidence. Acceptance criteria turn opinions into pass or fail.
```

## Types of testing, in plain words

| Level | Question it answers | Who usually does it |
| --- | --- | --- |
| Unit | Does this small piece work? | Developers |
| Integration | Do the pieces work together? | Developers and testers |
| System | Does the whole system work? | Test team |
| Performance | Does it hold up under load? | Specialist testers |
| Security | Can it be attacked? | Security team or specialist |
| User acceptance (UAT) | Does it do what the business needs? | Business users |

```ref
ISTQB | Test levels and test types | Unit, integration, system, acceptance. Name the owner of each level.
OWASP | Web Security Testing Guide | A source for security test cases when the application is web based.
```


## From requirement to criterion

A requirement says what. Acceptance criteria say how you will know.

```accordion
Order status must be accurate | Given an order shipped today, when a customer opens tracking, then the status matches the warehouse record within five minutes.
The portal must be fast | Given 500 concurrent users, when they open the order page, then ninety five percent of pages load within three seconds. The numbers are examples to agree with the business.
Only the right person sees an order | Given customer A is signed in, when they request customer B's order, then access is denied and the attempt is logged.
```

```ref
ISO | ISO/IEC 25010 product quality model | Gives quality words beyond bugs: reliability, security, usability, maintainability, performance efficiency.
```


## Your decision

Two weeks before launch, testing finds a medium severity defect. Daniel says "launch anyway and fix it later".

```decision
? What do you do?
- Agree, to protect the date | If the defect is on a critical path it can become an incident. You also teach the team that criteria are optional.
- Refuse, because the criteria say no open medium defects | Rigid, and it ignores the actual business impact. The sponsor may overrule you.
+ Check the agreed exit criteria, describe the real impact and the workaround, and let the sponsor and CISO make an informed, documented decision to accept or fix | The decision is made with evidence, recorded, and owned by the right people.
= Quality gates exist so that exceptions are conscious and documented, not accidental.
```

## Quality and AI

```cards
brain | Accuracy is a quality criterion | Agree a measurable standard on a test set before launch. | Judging accuracy by a few impressive demos.
users | Human review | Decide who reviews answers and how often. | Unreviewed answers reach customers.
eye | Monitoring after launch | Track wrong answers and complaints. | Quality decays quietly.
```

```ai
Shift | AI accuracy is a quality attribute and needs a number, not an adjective.
Example (illustrative) | Acceptance for an assistant says accurate. The PM agrees a test set of real questions and a ninety percent style threshold with the business before build, and records it.
Use AI to | Suggest acceptance criteria and generate test cases.
Keep human | Agreeing the threshold with the business before build.
Risk | Disputes at acceptance because accurate meant different things to different people.
Control | Define a test set, a threshold, a rule for citations and a route to a human, then monitor after launch.
Interview line | I treat AI accuracy like any other acceptance criterion: a number on a defined test set, agreed with the business before build, and monitored after launch.
```

```ref
NIST | AI RMF trustworthy characteristics: valid and reliable, safe, secure, accountable, explainable, privacy enhanced, fair | Use the list to write AI acceptance criteria that go beyond accuracy.
```

```cards
cpu | AI engineer | Builds the evaluation set and reports accuracy against the threshold. | Quality shown as a demo, not a rate.
handshake | Forward deployed engineer | Supplies real examples from users for the test set. | Test set built from the team's own wording.
shield | AI security consultant | Adds safety and privacy tests to acceptance. | Safety tested after acceptance.
wrench | Agent harness engineer | Builds the test harness that runs the set and records results. The term is not standardised, so confirm the scope. | Results not reproducible.
code | Traditional developers | Test integrations and fallbacks. | Fallback never exercised.
```

```incident
# Acceptance that said it works (illustrative)
What happened | An assistant was accepted after a successful demo. After launch users found it failed on a common type of question.
Impact | Complaints rose, and the business disputed whether the project had met its requirements.
Root cause | Acceptance criteria were not measurable and no test set of real questions existed.
Resolution | The team built a test set from real tickets, agreed a pass threshold and added a regression run to each release.
PM move | Agree the test set and threshold before build, and re run them on every change.
```

## Check your understanding

```quiz
? Which is a well formed acceptance criterion?
- The system should be reliable
+ Given 500 concurrent users, 95 percent of pages load within 3 seconds
- Users should be happy
= It is specific and testable with a clear pass or fail.
```

```comm
# Agree what done means before testing starts
Audience | Marcus Webb and the business owner, who disagree about when a feature is done
Situation | The feature works but the owner says it is not finished because the screen is slow.
Task | Write two acceptance criteria, one functional and one performance, that both of them can sign.
Good looks like | Each criterion has a measurable condition and a way to check it, for example a defined response time on a defined number of users. Neither depends on opinion.
```

```answer
? How do you define quality and acceptance on a project?
- Quality means no bugs | Quality is fitness for purpose, which includes usability, performance and safety.
- The customer will tell us if it is wrong | Waiting for complaints is correction, which costs more than prevention.
+ I define quality with the business in measurable terms before build: acceptance criteria with a clear pass or fail, test types such as functional, performance, security and user acceptance, and who signs off. I plan prevention first because it is cheaper than correction. For AI I agree a test set and an accuracy threshold and re run them on every change.
= Prevention costs less than correction.
= Make criteria pass or fail.
= Say who signs off.
```

## What to remember

```checklist
Quality is defined in advance and proven with evidence
Prevention costs less than inspection
Acceptance criteria are specific and testable
Exit criteria let you decide about exceptions openly
AI accuracy needs a number, a test set and monitoring
```
