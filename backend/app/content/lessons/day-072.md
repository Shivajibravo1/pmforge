## "It works on my machine"

A Nimbus developer's code runs perfectly on their laptop, fails in test and behaves differently again in production. Three environments, three sets of settings, and a long thread about whose configuration is wrong.

```chat
# Channel, Tuesday, 2:20 PM
Developer | Portal team | It works on my machine.
Operations lead | Operations | It does not work on ours. Somebody changed a setting by hand last month.
Rahul Mehta | Lead developer | We cannot say what is different. Nothing is written down.
```

Three technologies address this problem: containers package an application with what it needs, Kubernetes runs and manages many containers, and infrastructure as code describes the environment in files so it can be created repeatedly. A project manager does not need to operate them. You need to know what they change about risk, effort and governance.

```key
Containers make the application portable. Kubernetes makes running it at scale manageable. Infrastructure as code makes the environment repeatable and reviewable.
```

## Containers in plain language

A container bundles an application and its dependencies into a single package that runs the same way anywhere a container runtime is available. Think of a shipping container: the contents are packed once, and any ship, train or truck can carry it.

```cards
box | Docker image | A package with the application and what it needs. | Large images with outdated components.
server | Container | A running instance of the image. | Containers running as administrator.
database | Registry | A store for images, with access control and scanning. | Public images with unknown content.
```

```ref
NIST | SP 800-190 application container security guide | Cite it when security of containers comes up.
```


## Kubernetes in plain language

Kubernetes is a system that runs containers across many machines, restarts failed ones, scales up and down and rolls out updates in a controlled way. Managed offerings such as Azure Kubernetes Service remove much of the infrastructure work, but the team still owns configuration, security and cost.

```cards
layers | Cluster | The group of machines that run the workloads. | Too large, too small or unsecured.
repeat | Deployments | Describe the desired state, and the system works to keep it. | Misconfigured limits that cause outages.
network | Services and networking | Controls how parts talk to each other and the outside. | Open networks inside the cluster.
key | Secrets and access | Who can do what in the cluster. | Wide administrator rights.
```

```ref
CIS | Benchmarks for Docker and Kubernetes | A measurable baseline for hardening clusters and images.
OWASP | Kubernetes Top Ten | Common cluster risks you can add to your RAID log.
```

## Infrastructure as code

```flow
Describe | Write the environment in code, such as Terraform or Bicep
Review | Peers review the change like application code
Test | Validate and plan before applying
Apply | The pipeline creates or updates the environment
Record | History shows who changed what, and when
```

```accordion
Benefits | Repeatable environments, fewer manual errors, documentation by design and faster recovery.
Risks | A mistake can be applied at scale. State files and credentials need protection.
Drift | Manual changes make reality differ from the code. Detect and correct it.
```

Tool names and features change. Check current documentation for the tools in your organisation.

```ref
CIS | Controls v8, secure configuration of enterprise assets and software | Infrastructure as code makes configuration reviewable. Insist on code review and version control.
```


## Your decision

The team proposes moving all applications to Kubernetes, because it is modern. Operations has no Kubernetes experience.

```decision
? What do you advise?
- Approve, because the industry is moving that way | You add a complex platform with no skills to run it.
- Reject, because it is too risky | You block a useful option without testing it.
+ Start with one suitable application, use a managed service, include training and support in the plan, and decide on wider use after evidence on effort, reliability and cost | You learn at small scale and avoid betting everything on a fashion.
= Match the technology to the problem and the skills. Pilot first.
```

## What the PM should ask

```checklist
Is the application suited to containers, and is there a business reason
Who has the skills to run it, and how will others learn
Where are images stored, scanned and approved
How are secrets managed
Is the environment defined as code and reviewed
How is cost tracked per workload
What is the support model
```

## AI workloads

```cards
server | Model serving | Containers and clusters often host models and tools. | Expensive GPU resources left running.
lock | Isolation | Separate AI workloads and sensitive data. | One shared cluster with weak boundaries.
key | Tool access | Agents calling tools need tight permissions. | Broad service accounts.
```

```ai
Shift | AI workloads run in containers with GPUs and tokens as new cost and risk factors.
Example (illustrative) | An AI service runs in containers. The PM learns that outbound network access is open and asks for egress limits and scanned images.
Use AI to | Draft infrastructure as code and explain configs.
Keep human | Approving what is deployed. A person with authority signs off each model, image and permission before it runs.
Risk | Unscanned images, open egress and costs that grow unseen.
Control | Scan images, limit network egress, scope permissions per tool and monitor GPU and token costs. Record who approved each deployed model.
Interview line | For AI workloads in containers I scan images, limit egress, scope tool permissions, watch GPU and token costs and record who approved each model.
```

```ref
NIST | AI RMF Map function | AI workloads need GPUs, data and cost controls. Add them to the plan.
OWASP | Top 10 for LLM Applications | Include model and data supply chain risks in the platform review.
```

```cards
cpu | AI engineer | Needs GPU nodes, model images and reproducible environments. | Works in a notebook that cannot be rebuilt.
wrench | Agent harness engineer | Packages services, defines infrastructure as code and policies. The term is not standardised, so confirm the scope. | Hand built environments.
shield | AI security consultant | Reviews images, secrets and network policy. | Public images used unchecked.
users | Platform team | Runs the clusters and quotas. | Capacity planned by request.
money | FinOps lead | Watches GPU cost and idle capacity. | GPU nodes left running.
```

```incident
# AI service worked in a notebook, failed in production (illustrative)
What happened | A prototype worked in a data scientist's environment. The team deployed by copying files to a server and it failed with different library versions.
Impact | The release slipped while the environment was rebuilt by hand.
Root cause | No container image or infrastructure as code defined the environment.
Resolution | The team containerised the service, pinned versions, defined infrastructure as code and added the build to the pipeline.
PM move | Require a reproducible build for every AI service.
```
