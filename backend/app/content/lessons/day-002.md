## Wednesday, the scope meeting

Yesterday you triaged. Today Daniel Okafor, the sponsor, calls Nimbus into one room for an hour. On the whiteboard he has written one line: "Customers track their own orders, and an AI assistant answers their questions."

You look around the table. Everyone nods. You have learned that nodding is not agreement.

```chat
# Scope meeting, Wednesday, 10:00 AM
Daniel Okafor | Sponsor | It is a customer portal. Same as we built for the loyalty app last year. Same team, same plan.
Rahul Mehta | Lead developer | The portal is fine. The order history comes from the old system, and that data is a mess.
Elena Rossi | CISO | Customers will log in. That is an identity project hiding inside this.
Marcus Webb | Business analyst | And the assistant answers questions about orders. Which orders? Whose data does it see?
```

Daniel wants one project plan, one risk list, one date. Four of the people in this room just described four different kinds of project. If you plan it as "the portal" you will meet each of those surprises later, at the worst price.

```note
Fictional case. The pattern is real: the label on the project hides the work inside it.
```

## Name the type before you plan

Every IT project has a type. The type tells you what to worry about before anyone writes a line of code.

```cards
code | Application | A new portal, mobile app or ERP module. | Scope keeps growing and users do not adopt it.
server | Infrastructure | Network upgrade, data centre move, laptop rollout. | Downtime and hidden dependencies you only discover during cutover.
database | Data | Migration, warehouse, reporting. | Bad data quality, and numbers that do not reconcile after the move.
shield | Security | Identity rollout, zero trust, fixing vulnerabilities. | It disrupts the business or silently misses systems.
brain | AI | Chatbot, forecasting, document automation. | Unclear value, poor data, answers nobody can predict.
```

| Type | Typical examples | Main risk | Success looks like |
| --- | --- | --- | --- |
| Application | New portal, mobile app, ERP module | Scope growth, user adoption | Users complete real tasks, defects within threshold |
| Infrastructure | Network upgrade, data centre move, endpoint rollout | Downtime, hidden dependencies | No unplanned outage, documented rollback |
| Data | Migration, warehouse, reporting | Data quality, reconciliation | Reconciled counts, signed-off data owners |
| Security | Identity rollout, zero trust, vulnerability remediation | Business disruption, incomplete coverage | Measured risk reduction, audit evidence |
| AI | Chatbot, forecasting, document automation | Unclear value, data readiness, model behaviour | Measured accuracy and business impact, governance in place |

```ref
PMI | PMBOK Guide, tailoring the approach to the project | Interview line: you name the project type first, then tailor governance, lifecycle and controls to it instead of using one template everywhere.
```


## What happens if you get it wrong

Here is the same project run two ways. Read the timeline and notice where the money and trust leak.

```timeline
Week 2 | Plan written as one "portal" project, one risk list | info
Week 5 | Order history import finishes. Counts look fine on screen | ok
Week 9 | A customer finds her last three orders missing. Support sees four more like it | bad
Week 10 | Reconciliation shows about 4 percent of records lost in migration. Nobody owned the data workstream | bad
Week 11 | Launch slips three weeks, Elena opens a security review on the data handling | warn
```

The percentage is illustrative, but the pattern is common: a data problem nobody named as a workstream. Compare it with the same project where you named the types on day one.

## Most projects are mixed

Nimbus is an application project. It also needs login (security), a connection to order history (data), enough capacity (infrastructure) and an AI assistant (AI). The rule: name one primary type, then list the others as workstreams, each with its own owner. That way nothing falls between teams.

```diagram
# Nimbus: one primary type, four workstreams
zone Users
node cust | users | Customers | Track their orders
node staff | users | Service desk | Supports customers
zone Experience
node web | globe | Web portal
node app | phone | Mobile app
node ai | bot | AI assistant | A project type of its own
zone Services
node order | workflow | Order tracking
node signin | key | Sign-in | Security workstream
node notify | bell | Notifications
zone Data and platform
node db | database | Order history | Data workstream
node cloud | cloud | Cloud hosting | Infrastructure workstream
edge cust > web | Browse
edge cust > app
edge staff > ai | Support view
edge web > signin | Log in
edge web > order | Status
edge ai > order | Lookup
edge order > db | Reads
edge order > notify | Triggers
edge notify > cloud | Runs on
```

Read it top to bottom: what the customer sees depends on services, which depend on data, which depend on the platform. Security cuts across every layer. Each layer is a workstream somebody must own.

```flow
What is the main thing delivered? | Names the primary type
What is hardest to reverse if it fails? | Shows where the risk sits
Who must sign off before go-live? | Shows the real gatekeepers
```

```ref
ITIL | ITIL 4 project management practice and the service value chain | Shows that a mixed project (app plus infra plus data) still has to land as a managed service. Mention it when asked about handover to operations.
```


## Your decision

Daniel is waiting. He wants one line in the plan.

```decision
? Daniel asks you to keep it as one simple "portal project". How do you respond?
- Agree, to keep the sponsor happy, and handle the details later | The plan is simple and wrong. The data workstream has no owner and the loss appears in week 9, when fixing it costs the most.
- Push back hard and rewrite the project as five separate projects | You lose Daniel's support and create four extra governance meetings. The work was never separate, it was shared.
+ Keep one project with portal as the primary type, and show four named workstreams with an owner each | Daniel keeps his single date and single budget. Elena owns security, Rahul owns data load, Marcus owns assistant scope, and the risks have a home from week one.
= Do not argue about labels. Keep one project for the sponsor and make the hidden work visible as workstreams. Visibility with ownership is what protects you.
```

## The AI assistant is its own project type

Daniel said it casually: "and the AI assistant." This is the most common request project managers get today, and it is a different kind of work from a normal feature.

```cards
brain | Value must be measured | Decide up front how you will know the assistant helps, for example fewer contact centre calls. | A demo wows executives but nobody defined success, so nobody can say if it worked.
database | Data readiness | The assistant is only as good as the order and product data behind it. | Messy records produce confident wrong answers to real customers.
shield | Governance | Decide who reviews its answers and when a human takes over. | Shipping with no human fallback when it gets an order status wrong.
```

```ai
Shift | An AI project is mostly a data and governance project wearing an application costume. The model is a small part of the work.
Example (illustrative) | A team plans a staff help assistant as an app release. A review notes the data is scattered across three systems, so data readiness becomes the first workstream.
Use AI to | Compare project types, draft a first list of workstreams and check whether your plan has gaps for data, security and operations.
Keep human | Naming the project type. Only you know the contract, the data owners and the sponsor's real expectations.
Risk | Planning an AI assistant like a normal app release, so data readiness, evaluation and monitoring never appear in the plan.
Control | Ask early what data it uses, who owns it, who checks the answers and what happens when it is wrong.
Interview line | I name the project type first. For AI I add data readiness, evaluation, security review and monitoring to the plan.
```

```ref
NIST | AI RMF Map function and ISO/IEC 42001 (AI management system standard) | Use these to explain why an AI assistant needs its own purpose, owner and risk review before build. ISO/IEC 42001 is certifiable, so ask whether the client needs it.
```

```cards
cpu | AI engineer | Defines retrieval, prompts and evaluation. Needs data access and a quality threshold. | Treated as a software developer with a new tool.
handshake | Forward deployed engineer | Tunes the assistant on the customer's real data and questions. | Tuning stays on one laptop.
shield | AI security consultant | Reviews abuse cases, access rights and data flows. | Security treated as a late gate.
database | Data engineer | Prepares and secures the documents the assistant answers from. | Data readiness assumed, not checked.
code | Traditional developers | Build the surrounding application and integrations. | Plan assumes model behaviour is as predictable as code.
```

```incident
# An AI assistant was planned like an app release (illustrative)
What happened | A team planned an internal assistant as a standard application project with fixed requirements and a single test phase.
Impact | Answer quality was uneven, the schedule slipped and trust in the pilot dropped.
Root cause | The project type was never named, so data readiness, evaluation and iteration were missing from the plan.
Resolution | The team added a discovery stage, a data readiness check, an evaluation set and staged pilots, and reset expectations with the sponsor.
PM move | Name the project type before planning, and add the stages that type needs.
```

```quiz

- A pure data project
+ Primary type application, with security and data as workstreams that each have an owner

```

```comm
# Explain the project type in one breath
Audience | Daniel Okafor, a sponsor who thinks Nimbus is just a website
Situation | He asks why you are planning four workstreams and an AI assistant instead of one build plan.
Task | Explain in three sentences why the type of project changes how you plan, using one example from Nimbus.
Good looks like | Names the main type, says what extra work the secondary types add, and ties it to a plain consequence such as the security review or data checks. Uses his words, not engineering words.
```

```answer
? How do you decide what type of project you are running, and why does it matter?
- It does not matter, a project is a project | Different types carry different risks, skills and stages.
- I go by what the sponsor calls it | Labels are often wrong. You must read the work itself.
+ I name the type first: application, infrastructure, data, security or AI. Each has different risks, specialists and stages. An application needs requirements and testing, infrastructure needs change windows and rollback, data needs quality checks, security needs threat review and AI needs data readiness, evaluation and iteration. Most projects are mixed, so I plan for the strongest risk.
= Show you can name the risk that defines each type.
= Say most real projects are mixed. It shows realism.
= For AI, name the extra stages: data readiness, evaluation, staged pilot.
```

## What to remember

```checklist
Name the project type before planning
Five types: application, infrastructure, data, security, AI
Each type has its own main risk and its own meaning of success
Mixed projects: one primary type, others as workstreams with owners
Do not argue about labels, make the hidden work visible
An AI assistant adds data readiness and governance work
```
