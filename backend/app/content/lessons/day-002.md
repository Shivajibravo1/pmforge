## The wrong tool for the job

Imagine two projects land on your desk in the same week.

```quote
Build a new customer portal where people can track their orders. | Head of Sales
Move ten years of customer records from the old system to the new one. | Head of Operations
```

Both sound like "IT projects". A new PM often runs them the same way: same plan, same risks, same team. The portal goes fine. The migration quietly loses 4 percent of the records, and nobody notices until a customer calls.

```note
Illustrative example. The point is that the type of project changes what can go wrong.
```

## The five types

Before you plan anything, name the type. It tells you what to worry about.

```cards
code | Application | A new portal, mobile app or ERP module. What goes wrong: scope keeps growing and users do not adopt it.
server | Infrastructure | Network upgrade, data centre move, laptop rollout. What goes wrong: downtime and hidden dependencies.
database | Data | Migration, warehouse, reporting. What goes wrong: bad data quality and numbers that do not reconcile.
shield | Security | Identity rollout, zero trust, fixing vulnerabilities. What goes wrong: it disrupts the business or misses systems.
brain | AI | Chatbot, forecasting, document automation. What goes wrong: unclear value, poor data, unpredictable behaviour.
```

## What success looks like for each

"Done" means something different depending on the type.

| Type | Typical examples | Main risk | Success looks like |
| --- | --- | --- | --- |
| Application | New portal, mobile app, ERP module | Scope growth, user adoption | Users complete real tasks, defects within threshold |
| Infrastructure | Network upgrade, data centre move, endpoint rollout | Downtime, hidden dependencies | No unplanned outage, documented rollback |
| Data | Migration, warehouse, reporting | Data quality, reconciliation | Reconciled counts, signed-off data owners |
| Security | Identity rollout, zero trust, vulnerability remediation | Business disruption, incomplete coverage | Measured risk reduction, audit evidence |
| AI | Chatbot, forecasting, document automation | Unclear value, data readiness, model behaviour | Measured accuracy and business impact, governance in place |

## Most projects are mixed

A customer portal is an application project. But it also needs login (security), a link to the customer database (data) and enough server capacity (infrastructure).

The rule: name one primary type, then list the others as workstreams, each with its own owner. That way nothing falls between teams.

```flow
What is the main thing delivered? | Names the primary type
What is hardest to reverse if it fails? | Shows where the risk sits
Who must sign off before go-live? | Shows the real gatekeepers
```

## Check your understanding

```quiz
? A new customer portal needs single sign-on and a link to the customer database. How do you frame it?
- A pure data project
+ Primary type application, with security and data as workstreams that each have an owner
- Three separate unrelated projects
= One primary type, other types as owned workstreams. That keeps risks visible and nobody assumes someone else has it.
```

## What to remember

```checklist
Name the project type before planning
Five types: application, infrastructure, data, security, AI
Each type has its own main risk and its own meaning of success
Mixed projects: one primary type, others as workstreams with owners
```
