## "We shipped the model. Why is it getting worse?"

Six weeks after the support assistant pilot launched, complaints are rising. Nothing broke. No release happened. The provider updated the underlying model, the policy documents changed and customers began asking questions nobody had tested.

```chat
# Review, Monday, 3:00 PM
Priya Nair | Service desk lead | Customers say the answers are less helpful than in the pilot.
Rahul Mehta | Lead developer | The model version changed under us on the provider side. We did not re run the tests.
Data lead | Data team | And three policy documents were updated and nobody told us.
Victoria Hale | COO | Who owns the quality of this thing?
```

Traditional software changes only when you change it. AI systems change when data changes, when the model changes, when prompts change and when users change. MLOps is the set of practices for building, deploying and operating machine learning systems reliably. LLMOps applies similar ideas to systems built on large language models, with extra attention to prompts, retrieval, evaluation and safety.

```key
In AI delivery, the lifecycle does not end at launch. Evaluation, monitoring, versioning and controlled change are the core of operations.
```

## The lifecycle

```flow
Frame | Problem, users, thresholds
Data | Collect, check, curate and version
Build | Prompts, retrieval, models and tools
Evaluate | Test on a fixed evaluation set and with humans
Deploy | Staged release with guardrails and fallback
Monitor | Quality, safety, cost, drift and feedback
Improve | Update data, prompts and models under change control
```

```ref
ISO | ISO/IEC 5338 AI system life cycle processes | The lifecycle continues after release. Operation and monitoring are part of the plan.
NIST | AI RMF Manage function | Allocate resources to treat and monitor risks over time.
```


## What to version

```cards
brain | Model and settings | Which model, version and parameters. | Untracked provider updates.
pencil | Prompts and instructions | Treated as code, reviewed and tested. | Edits made live to fix one complaint.
database | Data and documents | Which sources and versions the assistant used. | Unknown content behind an answer.
chart | Evaluation sets and results | Fixed tests and scores per version. | No way to compare changes.
```

```ref
NIST | SP 800-218 SSDF | Version code, data, prompts, model and configuration so any change can be traced.
```


## What can change quality

```timeline
Day 1 | Pilot launches, evaluation passes | ok
Week 2 | Provider updates the underlying model version | warn
Week 3 | Policy documents revised, index not rebuilt | warn
Week 4 | New seasonal questions appear that nobody tested | warn
Week 6 | Complaint rate climbs, no alert fired | bad
```

## Controls that catch it

```accordion
Pin versions | Use a fixed model version where the provider allows it, and plan the upgrade.
Regression evaluation | Re run the evaluation set before any change and on a schedule.
Data change process | Document updates trigger an index refresh and a test.
Monitoring | Track answer ratings, escalation rate, refusals, complaint topics and cost.
Feedback loop | Easy ways for users and staff to flag wrong answers, which feed the evaluation set.
```

```ref
DORA | Delivery metrics | Release and recovery metrics apply to AI delivery too.
```


## Your decision

The team wants to fix the complaints by editing the prompt live in production, to be quick.

```decision
? What do you recommend?
- Edit the prompt live, since it is only text | A change that nobody tested can break other answers, and nobody can trace it.
- Freeze all changes until a full re test | Safe but slow, and the complaints continue.
+ Make the change in a branch, run the evaluation set including the complaint cases, release to a small share of traffic, compare, then widen, with the previous prompt ready to restore | A prompt is a release. It gets the same discipline, but with a fast route.
= Treat prompts and data as releasable assets. Test, stage and keep a way back.
```

## Health

```rag
Version control | A | Prompts in a repository, model version not pinned
Evaluation | A | Exists, not automated
Monitoring | R | No quality alerts
Change process | A | Informal for prompts and documents
Ownership | R | Service owner unclear
```

**Levels of maturity**

```accordion
Level 1 | Manual: tests run by hand, changes in production, no monitoring.
Level 2 | Repeatable: versioned prompts and data, scheduled evaluations.
Level 3 | Automated: evaluation in the pipeline, staged release, monitoring and alerts.
Level 4 | Governed: audit trail, policy gates, regular review and incident drills.
```

Maturity descriptions vary between organisations and vendors. Use them as a conversation guide, not a standard.


```ai

```

```cards
wrench | Agent harness engineer | Owns versions of tools, prompts and guardrails, plus run logs and evaluations. The term is not standardised, so confirm the scope. | A prompt edited live with no version.
cpu | AI engineer | Owns the evaluation set and the data, prompt and retrieval versions. | Changes tested only on a few examples.
compass | Harness platform engineer | Builds the pipeline that promotes versions with gates and rollback, for example on the Harness CI/CD platform. | Manual releases with no rollback.
bot | Forward deployed engineer | Reports issues seen in the customer environment back into the backlog. | Field fixes that never become versioned changes.
shield | AI security consultant | Reviews changes that touch data, permissions or tools. | Reviews skipped for small changes.
```

```incident
# A production prompt was edited to fix one complaint (illustrative)
What happened | Someone edited a prompt directly in production to fix a single complaint.
Impact | Other answers got worse and nobody could tell what had changed.
Root cause | Prompts, retrieval settings and model versions were not versioned or tied to an evaluation run.
Resolution | The team rolled back to the last versioned prompt, then required review, an evaluation run and release through the pipeline.
PM move | Treat prompts, data and configuration as versioned release artefacts under change control.
```

## Check your understanding

```quiz
? Why should prompts be treated like code?
- Prompts never change
+ Small prompt edits can change behaviour widely, so they need review, tests and version history
- Prompts are secure by default
= Prompts affect behaviour and need version control and testing.
```

```answer
? How do you keep an AI system's quality from degrading after launch?
- Fix issues as users report them | Reactive, and unversioned edits can make things worse.
- Retrain the model regularly | Not every system retrains. The cause may be data, prompts or a provider change.
+ I version everything that can change quality: data, prompts, model version, retrieval settings and the evaluation set. Every change runs the evaluation set before release, ships in stages with rollback, and goes through change control. In production we monitor quality, safety, cost and drift with named owners.
= List what you version. It shows you understand the real causes of change.
= Say every change is evaluated before release.
= Mention rollback. It signals production maturity.
```
