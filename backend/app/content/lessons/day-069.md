## From commit to customer

A developer fixes a small bug in the Lighthouse portal on Monday. It reaches customers on Thursday of the following week. Between the fix and the customer there were nine steps, five handovers and two waits for approvals.

```chat
# Message, Tuesday, 3:10 PM
Developer | Portal team | The fix was one line. It took eleven days to get out.
Operations lead | Operations | Each step has a reason. I would not skip any of them.
Priya Nair | Service desk lead | My team told customers it would be fixed Friday.
```

A CI/CD pipeline automates the path from code to production. Continuous integration builds and tests every change as it is merged. Continuous delivery keeps the code always in a releasable state, and continuous deployment goes further by releasing automatically after checks pass.

```key
A pipeline turns release knowledge into an automated, repeatable and auditable path. The goal is not speed alone, but safe, predictable change.
```

## The stages

```flow
Commit | A developer pushes a change to the repository
Build | Code is compiled and packaged
Test | Automated unit, integration and quality checks
Scan | Security scans for code, dependencies and secrets
Deploy to test | Package is released to a test environment
Approve | Automated gates or manual approval
Deploy to production | Release with a safe strategy
Monitor | Check health and user impact
```

```ref
NIST | SP 800-218 SSDF | Map pipeline stages to SSDF practices: protect the code, produce well secured software, respond to vulnerabilities.
OWASP | Top 10 CI/CD Security Risks | Use it to ask about pipeline access, secrets and third party packages.
```


## What each stage protects against

```cards
check | Automated tests | Prevent known behaviour from breaking. | Slow, flaky tests that people ignore.
shield | Security scans | Catch vulnerable libraries and exposed secrets early. | Scans that run but nobody reads.
layers | Environments | Test in a place that resembles production. | Test environments that differ from production.
flag | Approval gates | Make the right people accountable for risky changes. | Gates that wait for a person for days.
eye | Monitoring | Detects problems after release. | Releases that nobody watches.
```

## Where time is lost

```timeline
Day 1 | Fix committed, waits for code review | warn
Day 3 | Manual test request in a queue | warn
Day 6 | Change request approval, weekly board | bad
Day 10 | Deployment window, only on Thursdays | bad
Day 11 | Released | info
```

## Quality gates that make sense

```accordion
Before merge | Peer review, build passes, unit tests pass, secret scan clean.
Before test deploy | Integration tests pass, dependency scan has no critical findings.
Before production | Smoke tests pass, approvals recorded, rollback tested.
After release | Health checks, error rates and key business measures stay within limits.
```

```ref
ISTQB | Test levels and automation | A quality gate should block on tests that matter. Too many gates slow flow, too few let defects through.
```


## Your decision

The change advisory board meets weekly. The team wants to deploy small low risk fixes without waiting for it.

```decision
? What do you do?
- Skip the board for everything, to go faster | You lose governance, and the first failure destroys trust.
- Keep the board for every change | Small safe fixes wait a week, and teams find workarounds.
+ Agree with the board and risk owner a standard change category for low risk, tested, reversible changes that the pipeline approves automatically and records, while larger or risky changes still go to the board | Governance moves into the pipeline, speed improves and risk is still controlled.
= Replace manual ceremony with automated evidence for low risk changes, and keep human judgement for high risk ones.
```

## Pipeline in Azure DevOps terms

```cards
git | Repos | Source code with branch policies and reviews. | Direct pushes to main.
workflow | Pipelines | Build and release defined as code in YAML. | Hand edited releases that cannot be reproduced.
list | Boards | Work items linked to commits and releases. | Changes with no traceable reason.
key | Variable groups and key vault | Secrets held outside code. | Secrets in the repository.
```

Names and features change over time. Check the current Azure DevOps documentation for exact terms.

## Pipeline health

```rag
Build time | G | Under ten minutes
Test reliability | A | Several flaky tests
Security scans | A | Run on build, not yet blocking
Approvals | R | Manual, weekly
Rollback | A | Documented, not rehearsed
```

## AI in the pipeline

```cards
search | AI test generation | More test cases quickly. | Tests that mirror the code and miss intent.
file | AI summarising failures | Faster diagnosis. | Wrong summaries taken as truth.
brain | Evaluating AI features | Run an evaluation set on every model or prompt change. | Shipping a prompt change with no regression test.
```

```ai
For AI features, add a stage that runs a fixed evaluation set and compares accuracy, safety and cost with the last version. Block release if thresholds are not met.
```
