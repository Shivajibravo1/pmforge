## From whiteboard to tool

Rahul, Marcus and you have a WBS on a wall and a critical path on a notebook page. Daniel wants it in the tool the programme office uses, so he can see it without asking you.

```chat
# Programme office, Friday, 9:00 AM
Daniel Okafor | Sponsor | I want to open one link and see what is late. Not a spreadsheet you email me.
Priya Nair | Service desk lead | Whatever you use, please make sure my team's tasks are in it, not only the developers'.
```

The tool is not the plan. A plan in Jira, Azure DevOps or a Gantt chart is only as good as the structure behind it. This lesson turns your WBS and critical path into something a sponsor can open and trust.

```key
Tools show the plan. They do not make it. Put the WBS, dependencies, owners and dates in, and the tool will tell the truth about progress.
```

## What the tool must contain

```cards
layers | Hierarchy | Epics or summary tasks mirror the WBS, with work packages below. | A flat list of tasks with no structure.
link | Dependencies | Links between tasks, especially those on the critical path. | Dates are typed in by hand and never update.
users | Owners | Exactly one named owner per task. | Tasks owned by a team, so nobody acts.
clock | Dates and baseline | Planned dates saved as a baseline so you can compare. | No baseline, so you cannot say what changed.
```

```ref
PMI | Practice Standard for Scheduling | The schedule model needs activities, dependencies, durations and resources. Check the tool holds all four.
```


## Choosing the format

| Tool | Best for | Watch out for |
| --- | --- | --- |
| Gantt chart (for example in a planning tool) | Predictive plans, critical path and dependencies | Becomes stale if nobody updates it |
| Jira or Azure DevOps boards | Agile delivery, backlog and sprints | Weak at long range dependencies unless you add them |
| Hybrid | Gantt for gates and milestones, boards for sprint work | Two sources of truth if not linked |

Lighthouse is hybrid, so the Gantt shows milestones and security gates, and the boards show the sprints inside them.

## Your decision

Rahul wants to track only in the sprint board. Elena needs gate dates visible. Daniel wants one view.

```decision
? How do you set it up?
- Use only the sprint board and drop the gates | Elena cannot see her dates, and the critical path vanishes from view.
- Keep two separate tools and update both by hand | Two sources of truth drift apart within a month, and the status becomes a debate.
+ Put milestones, gates and critical path dependencies in the planning view, link the sprint epics to those milestones, and publish one dashboard link for Daniel | One view for the sponsor, each team works in its own tool, and the dates stay linked.
= Pick one place for dates the sponsor sees, link the team tools to it, and name one source of truth for each type of information.
```

## Build order

```flow
Create the hierarchy | WBS levels become epics and tasks
Add owners | One named person each
Add dependencies | Especially the critical path
Add estimates and dates | From Day 16 and Day 17
Save the baseline | So change is visible
```

## AI inside the tools

```cards
spark | AI summaries | Many tools now offer summaries of boards and updates. | A summary of a plan with stale data is a confident stale summary.
file | AI generated tasks | An assistant can turn a charter into tasks. | Duplicates and missing dependencies.
lock | Access and data | Plans can contain confidential names and dates. | Enabling an AI feature without checking where the data goes.
```

```ai
Shift | Planning tools now ship AI features that draft work items and summarise boards. Speed rises, and so does the risk of noise.
Example (illustrative) | A planning tool offers to generate tasks from a requirements document. The PM checks the data settings, enables it for a test project and reviews every item.
Use AI to | Draft items from a WBS, remove duplicates and summarise status for the weekly review.
Keep human | Owners, estimates and dependencies. Review each generated item the way a developer will read it.
Risk | A flooded backlog, and project data sent outside the organisation by a feature nobody assessed.
Control | Check the tool's data settings before enabling anything, set a review step and name an owner for backlog quality.
Interview line | I let AI draft and deduplicate, then I review every item and check where the tool sends data before turning it on.
```

```ref
OWASP | Top 10 for LLM Applications, excessive agency | If an AI feature can create or change tickets, limit what it may do and keep a human approval.
```

```cards
cpu | AI engineer | Uses AI features in Jira or Azure DevOps to draft items, then reviews them. | Generated items accepted without reading.
shield | AI security consultant | Reviews what project data may be sent to AI features in tools. | Confidential data sent to features nobody assessed.
handshake | Forward deployed engineer | Works from the shared backlog so site changes are visible. | Private lists that do not reach the plan.
wrench | Agent harness engineer | Defines what an AI agent may change in the tool, if one is used. The term is not standardised, so confirm the scope. | Agent with write access to the whole backlog.
code | Traditional developers | Keep items small, linked and current. | Stale tickets that mislead the plan.
```

```incident
# AI generated tasks flooded the backlog (illustrative)
What happened | A team used an AI feature to generate tasks from a requirements document and loaded them straight into the backlog.
Impact | Duplicate and vague items appeared, the schedule looked bigger than it was, and developers lost trust in the plan.
Root cause | Output was not reviewed, and there was no rule for who owns the backlog quality.
Resolution | The team removed duplicates, set a review step for generated items and named an owner for backlog quality.
PM move | Treat AI output as a draft. Review before it enters the plan, and keep a named owner.
```

## Before you submit

```checklist
Hierarchy matches the WBS
Every task has one owner
Critical path dependencies are linked
Estimates and dates are present, with a saved baseline
A single view exists that a sponsor can open
Milestones for security gates are visible
```

```answer
? How do you set up a plan in a tool such as Jira or Azure DevOps?
- I load every task and let the tool track it | A tool shows the plan, but it does not make the plan good.
- I use the tool the sponsor likes best | Choose by team needs and reporting, not preference.
+ I start from the WBS and agree a simple structure: epics or features, work items with owners, estimates, dependencies and a few clear statuses. I pick the format that fits the team, a backlog for agile work or a Gantt for dated plans, and often both. I set up reports for the sponsor, review hygiene weekly and treat AI generated items as drafts that a person reviews.
= Mention the WBS as the source.
= Say how you keep the data clean.
= Mention AI as a draft helper, not an owner.
```

```mindmap
# Plan in a tool
Structure | WBS, epics, work items, owners
Format | Backlog, board, Gantt
Hygiene | Statuses, dependencies, weekly review
AI | Draft help, review, data rules
```

```flashcards
Start the tool plan from | The WBS and the agreed scope.
Backlog versus Gantt | A backlog suits iterative work. A Gantt suits dated plans with dependencies.
Tool hygiene | Clear owners, current statuses, linked dependencies and weekly review.
AI generated items | Drafts that a person must review before they enter the plan.
```
