## The wall between two teams

Nimbus releases happen four times a year. Each one takes a weekend and a long checklist. Developers write the code. Operations deploy it. When something breaks, each side says the other made a mistake.

```chat
# Release retrospective, Friday, 5:10 PM
Rahul Mehta | Lead developer | We hand over a package and a document. Then it is their problem.
Operations lead | Operations | We receive it with no context. We find out what changed when it fails.
Daniel Okafor | Sponsor | Customers do not care whose problem it is. They care that it is down.
```

DevOps is a way of working that removes the wall between those who build and those who run. It is not a tool and not a job title. It is a set of principles, practices and measures that let a team deliver small changes frequently, safely and with fast feedback.

```key
DevOps is about flow and learning: short feedback loops, shared ownership and automation of repetitive work, so change becomes routine and safe.
```

## Core principles

```cards

repeat | Small, frequent changes | Small changes are easier to test, understand and reverse. | Large releases with many risks.
settings | Automation | Build, test and deploy by machine, not by hand. | Manual steps that vary and fail.
eye | Feedback | Monitoring and user data inform the next change. | Flying blind after release.
book | Learning | Blameless reviews improve the system. | Hiding mistakes.
```

## The four key measures

The research programme known as DORA identified four measures that together describe software delivery performance. Check the current definitions and benchmark ranges on the DORA website, because the programme has evolved and the details have been updated.

```cards
rocket | Deployment frequency | How often you release to production. | Counting deployments that carry no value.
clock | Lead time for changes | Time from code committed to running in production. | Ignoring waiting time before commit.
alert | Change failure rate | Share of changes that cause a failure needing a fix. | Hiding failures by not recording them.
tool | Time to restore | How quickly you recover from a failure. | Measuring only successful days.
```

Speed and stability are not opposites in this research. Teams that perform well tend to be good at both.

```ref
DORA | The four key metrics: deployment frequency, lead time for changes, change failure rate, time to restore | Know all four. Say that speed and stability go together in DORA research.
```

## How to use the measures

```accordion
As questions | Where does the time go between commit and release. What causes failures.
For improvement | Track trends over months. Compare a team with itself.
Not as targets | If you reward frequency, people split changes artificially. If you punish failures, people stop reporting them.
Not for ranking people | They describe a system, not an individual.
```

## Your decision

A director wants a league table of teams by deployment frequency, to motivate them.

```decision
? What do you recommend?
- Publish the league table | Teams game the number, and weaker teams get blamed for system problems.
- Ignore the request | The director still wants evidence of progress.
+ Offer a trend dashboard per team with the four measures and a short explanation of causes, used in improvement conversations, not as a ranking | The director sees progress, teams stay honest and improvements target real constraints.
= Measures inform improvement. Ranking by a metric distorts the metric.
```

## AI and DevOps

```cards
code | AI coding assistants | More code written faster. | More code to review, test and secure.
file | AI in pipelines | Summaries of failures and suggested fixes. | Fixes applied without understanding.
brain | AI features need operations too | Models need monitoring, versioning and rollback like any service. | Treating a model as finished at launch.
```

```ai
Shift | When AI increases how fast code is written, review, testing and scanning must keep up.
Example (illustrative) | Developers ship faster with AI help. Review queues grow, so the PM adds reviewers and automated scanning to restore balance.
Use AI to | Write tests, summarise pull requests and suggest fixes.
Keep human | Review and approval. A person reads the change, understands it and accepts responsibility before it reaches production.
Risk | A bottleneck that moves, so risk grows quietly.
Control | Track the four DORA measures and make sure review capacity and scanning rise with code volume.
Interview line | AI speeds writing code, so I check that review, testing and security scanning keep up. Otherwise the bottleneck moves and risk grows quietly.
```

```cards
wrench | Harness platform engineer | Builds and runs delivery pipelines, feature flags and release strategies on the Harness CI/CD platform. Check vendor documentation for current features. | Pipelines hand built per team with no shared templates.
cpu | Agent harness engineer | A different role with a similar name. Builds the tools, memory, guardrails and evaluations around an AI agent. The term is not standardised. | Two harnesses confused in a plan, so neither is staffed.
bot | Forward deployed engineer | Deploys and tunes releases in the customer environment, often with limited pipeline access. | Manual fixes on site that bypass the pipeline.
brain | AI engineer | Adds evaluation runs and model or prompt versions to the pipeline. | Releases with no quality gate for model behaviour.
shield | AI security consultant | Reviews pipeline secrets, agent permissions and supply chain risk. | Findings arrive after release.
```

```incident
# Agent released to everyone with no rollback (illustrative)
What happened | A new agent version passed unit tests and was released to all users at once. It began calling a ticket tool far more often than expected.
Impact | The ticket queue filled with duplicates and the integration hit its rate limits.
Root cause | The pipeline had no staged rollout, no call rate limit and no evaluation stage for agent behaviour.
Resolution | The release was switched off with a feature flag, then redeployed as a canary with call rate alerts and an evaluation stage.
PM move | Add agent behaviour checks and a canary stage to the definition of done, and track change failure rate and time to restore.
```
